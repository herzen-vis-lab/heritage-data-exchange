# Heritage Data Exchange
 
> **Prototype of a federated exchange protocol for digital cultural heritage objects between universities, museums, and libraries in a loosely coupled network.**
 
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)
[![Protocol Version](https://img.shields.io/badge/protocol-v0.0.8-green.svg)](docs/federated-exchange-document.md)
 
---
 
Разрабатывается в РГПУ им. А. И. Герцена
 
Протокол обмена для слабосвязанной сети независимых организаций — университетов, музеев и библиотек.
Решает три задачи: идентификация узлов без центрального оператора,
связывание карточек объектов между независимыми хранилищами, согласование классификаторов в федеративной топологии.
 
---
 
## Проблема / Problem
 
Существующие форматы описания культурного наследия (MARC21, Dublin Core, IIIF, EDM) создавались для **централизованных** каталогов. При переходе к децентрализованной сети независимых организаций они не решают три ключевых задачи:
 
- **Идентификация узлов сети** — нет механизма уникальной идентификации организации-источника при обмене данными между узлами слабосвязанной сети
- **Связывание записей между узлами сети** — нет стандартного протокола обнаружения дубликатов и взаимного обогащения записей
- **Совместимость классификаторов** — словари локальны, нет механизма согласования авторитетных источников между узлами сети
Проект исследует **протокол обмена для децентрализованной слабосвязанной сети** как альтернативу единому централизованному каталогу.
 
---
 
## Архитектурный подход
 
Протокол основан на паттернах федеративного управления данными, адаптированных к домену цифрового культурного наследия: каждый участник хранит данные локально и ведёт собственный реестр, а согласованность достигается обменом между узлами, а не центральным каталогом.
 
| **Паттерн** | **Реализация в проекте** |
|---|---|
| Идентификация карточки объекта | `digital_object_guid` (UUID v4) — уникальный идентификатор объекта в федерации |
| Связывание карточек объектов | Механизм обнаружения дубликатов между узлами + взаимное обогащение атрибутов |
| Классификация через авторитетные источники | `Classification.authority` (URI) — внешние словари (AAT, ULAN, LCSH, VIAF) |
| Федеративная топология | Каждый узел хранит данные локально; центральная система не требуется |
| Экспертное сопровождение данных | Атрибутирование с верификацией на уровне эксперта (`attribution_status`) |
 
**Почему федеративная топология, а не реестровая / звезда:**
организационная автономность участников и отсутствие доверенного центрального оператора — стандартные условия музейных консорциумов, университетских сетей и библиотечных объединений.

## Концептуальные границы

- Транспортный слой и механизм подписки на группы — предмет реализации и отдельной публикации; целостность и подлинность конверта обеспечиваются транспортным слоем (подпись, TLS).
- Единая каноническая карточка не выделяется: у каждого узла собственная карточка объекта; карточки связываются (`same_as`) и взаимно обогащаются по провенансу.
- Лицензии объектов задаются узлом `License` (код + authority) по аналогии с классификацией; authority может ссылаться на любой авторитетный источник, включая некоммерческую организацию (НКО) как один из вариантов.
- Использование атрибутов в обучающих данных моделей ИИ — только при `is_enabled_for_ai_using = true`; отсутствие флага означает запрет (консервативный дефолт).
- Сущности наследия моделируются как `Work` (абстрактная сущность; первый регистратор — владелец записи), `Manifestation` (реализация Work) и `Item` (физический/локальный экземпляр у узла-владельца); Items разных узлов не являются дубликатами.
- Приоритет по времени (первый регистратор) действует только для идентичности и владения записью и не является критерием истинности атрибутов; при расхождении атрибут хранится как множество заявлений (`Claim`) с провенансом, каноническое значение — по явному правилу (предлагаемый по умолчанию порог N≥2 независимых подтверждений, окно оспаривания, fallback).
- Дедупликация (matching) и принятие атрибутов (acceptance) — раздельные события; регистрация работ третьих лиц требует `rights_holder_confirmation`.

## Что реализовано
 
- [UML-модель протокола обмена v0.0.8](docs/federated-exchange-document.md) + асинхронный транспортный конверт: один тип `publish` с двумя режимами (broadcast — полный снимок; таргетированный — возврат вклада получателя)
- [JSON Schema модели данных](schema/federated-exchange-document.schema.json) и [JSON Schema конверта обмена](schema/exchange-envelope.schema.json)
- [Правила протокола](docs/federated-exchange-document.rules.dsl): провенанс атрибутов, жизненный цикл дедупликации, согласование классификаторов, лицензии объектов и использование данных в ИИ
- [Примеры обмена между организациями А и Б](examples/README.md): broadcast-публикация полного снимка и таргетированный возврат вклада (сценарий из статьи)
- [Каталог экспозиций РГПУ им.А.И. Герцена](https://collections.herzen.spb.ru/) как пример сервиса для создания и распространения объектов цифрового культурного наследия

## Контекст и публикации
 
**Область применения:** университеты, музеи, библиотеки и прочие организации с накопленным культурным наследием и потребностью в совместном цифровом каталоге без централизованного оператора.
 
**Культурологическая рамка:** университетское наследие — педагогические тексты, методики кафедр, студенческие работы — образует особый слой культурного наследия, слабо представленный в ведомственных каталогах; децентрализованная сеть без центрального оператора позволяет сохранить разнообразие подходов к атрибуции и интерпретации наследия.
